# ZION Local API v1

The API base path is /v1 and defaults to 127.0.0.1:42001. Non-loopback binding requires an explicit bearer token and emits a startup warning. No wildcard CORS origin is accepted; exact configured development origins are echoed only after matching, including bounded `OPTIONS` preflight responses.

## Endpoints

- GET /v1/health returns liveness and readiness. A process can be live while UNINITIALIZED or SYNCING; readiness requires RUNNING and SYNCED.
- GET /v1/status returns network/genesis, lifecycle, roles, PeerID, sync status, accepted height, StateHash, consensus activity, validator authorization, protocol version, and bounded object-store usage (`object_store_enabled`, `object_count`, `object_bytes`, `object_quota_bytes`). It does not expose the store path.
- GET /v1/peers returns bounded usable general-P2P peers.
- GET /v1/state returns counts and a state summary, never a full unbounded snapshot.
- GET /v1/identities/{identity_id} and /v1/memberships/{identity_id} return public canonical information. Identity responses include the current public `active_key_id`; no private material is exposed.
- GET /v1/governance/proposals and /v1/governance/proposals/{proposal_id} inspect bounded canonical governance state. The client-safe JSON projection uses string `proposal_id`, kind, proposer IdentityID, status, start/end heights, electorate count, authoritative YES/NO/ABSTAIN/participant tallies, bounded votes with public KeyIDs, and the typed proposal payload. Lists accept offset and limit up to 100. This is a JSON projection only and does not alter canonical governance bytes.
- POST /v1/transactions accepts {"encoding":"base64","transaction":"..."} containing one already-signed canonical transaction.
- GET /v1/transactions/{tx_id} returns bounded recent local status.
- POST /v1/objects accepts `{"encoding":"base64","object":"..."}` containing exactly one complete canonical ZION object. It returns `object_id`, canonical byte `size`, and `STORED` (HTTP 201) or `ALREADY_EXISTS` (HTTP 200). Unknown wrapper fields and server-side paths are rejected.
- GET /v1/objects/{object_id} is local-only and returns `{"encoding":"base64","object":"...","object_id":"...","size":...}` with the exact verified canonical object bytes. It never performs implicit network retrieval.
- GET /v1/objects/{object_id}/meta returns verified `object_id`, `size`, `present`, and local `stored_at`; it never returns a filesystem path.
- POST /v1/objects/{object_id}/fetch checks local storage first, then uses bounded authenticated P2P retrieval. Success is `ALREADY_LOCAL` or `FETCHED`; timeout, no-peer, invalid-remote, quota, corruption, and not-found conditions use stable error codes.
- POST /v1/board/events accepts `{"encoding":"base64","event":"..."}` containing one already-signed canonical Board event object. It never signs for the caller. Successful local admission returns HTTP 201 with the indexed event and `post_id`.
- GET /v1/board/posts returns the bounded local feed. GET /v1/board/posts/{post_id} returns one indexed event, and GET /v1/board/posts/{post_id}/replies returns its bounded oldest-first reply thread. Lists accept `offset` and `limit` up to 100.
- GET /v1/board/search?q=... performs bounded local Unicode case-insensitive substring search over available Board text and reference metadata. It is local derived behavior, not a network or consensus query.
- POST /v1/board/posts/{post_id}/hide and `/unhide` update only local visibility. They do not delete objects or issue a global moderation action.
- GET /v1/research and GET /v1/resources return ID-sorted canonical registry projections with bounded `offset`/`limit` pagination (maximum 100).
- GET /v1/research/{research_id} and GET /v1/resources/{resource_id} require strict lowercase typed IDs and return one admitted immutable entry plus governance provenance.
- GET /v1/research/search?q=... and GET /v1/resources/search?q=... perform bounded local Unicode-safe search. Queries are at most 512 UTF-8 bytes and results are derived, not consensus decisions.

Submission can be REJECTED_LOCALLY, ACCEPTED_FOR_SUBMISSION, SUBMITTED_TO_CONSENSUS, KNOWN_ALREADY, or FINALIZED. Decode, relay, or CheckTx success is never represented as finality.

Errors use {"code":"STABLE_CODE","message":"bounded explanation"}. Bodies, headers, URIs, pagination, concurrent work, and server read/write/idle time are bounded. Transaction bodies retain the Phase 8 limit; object uploads have a separate fixed envelope bound sufficient for one base64-encoded 1 MiB canonical object. Responses contain no private keys, bearer tokens, server paths, or stack traces, and there are no admin membership, validator, or governance-bypass routes. Remote exposure should be protected by host firewall and TLS termination in addition to the required bearer token.

`zionctl --bearer-token-file <path> ...` reads remote-API credentials from a bounded local file without placing the token in command arguments or output.

Object CLI commands use only this API:

```text
zionctl object put <canonical-object-file>
zionctl object get <object-id> --out <file> [--force]
zionctl object stat <object-id>
zionctl object fetch <object-id>
```

`put` rejects directories, empty files, inputs above 1 MiB, and malformed/non-canonical objects before submission. `get` verifies canonical encoding and ObjectID before writing exact object bytes locally and refuses an existing output unless `--force` is supplied. No CLI output path is sent to the node.

Board CLI commands use only the versioned local API and never sign on behalf of the user:

```text
zionctl board submit <signed-event-object-file>
zionctl board feed
zionctl board get <post-id>
zionctl board replies <post-id>
zionctl board search <query>
zionctl board hide <post-id>
zionctl board unhide <post-id>
```

Board results distinguish signature validity, current membership, current authorization classification, content presence, parent presence, and local visibility. Board error codes include `INVALID_BOARD_EVENT`, `INVALID_BOARD_CONTENT`, `BOARD_EVENT_TOO_LARGE`, `BOARD_PUBLICATION_DENIED`, `BOARD_CONTENT_MISSING`, `BOARD_PARENT_NOT_FOUND`, `BOARD_POST_NOT_FOUND`, and `INVALID_BOARD_QUERY`. Internal paths and raw backend errors are not returned.

## Object examples and errors

Store canonical bytes (shown shortened only for readability):

```http
POST /v1/objects
Content-Type: application/json

{"encoding":"base64","object":"omFjb3JlLi4u"}
```

```json
{"object_id":"zion:obj:sha256:<64-lowercase-hex>","size":123,"status":"STORED"}
```

A local read returns the same canonical bytes in the `object` field. A fetch request has no body:

```http
POST /v1/objects/zion:obj:sha256:<64-lowercase-hex>/fetch
```

```json
{"object_id":"zion:obj:sha256:<64-lowercase-hex>","size":123,"status":"FETCHED"}
```

Stable object error codes include `INVALID_OBJECT_ID`, `INVALID_OBJECT`, `OBJECT_TOO_LARGE`, `OBJECT_NOT_FOUND`, `OBJECT_CORRUPT`, `OBJECT_STORE_FULL`, `OBJECT_FETCH_TIMEOUT`, `NO_OBJECT_PEERS`, and `INVALID_REMOTE_OBJECT`. `GET` never contacts peers; only the explicit fetch endpoint can start network work. Object results describe local storage/availability and never transaction commitment or finality.

Registry endpoints are read-only. Admission still requires a signed proposal, votes, finalization, and execution submitted through `/v1/transactions`; there is no direct registry mutation route. Entry `external_uri` is a mutable HTTPS location and is never fetched by consensus. ObjectIDs are immutable content identities; an `object_availability` item may report the local-only `present_local` hint, and clients may explicitly reuse `/v1/objects/{object_id}/fetch`.

Registry CLI commands are:

```text
zionctl research list
zionctl research get <research-id>
zionctl research search <query>
zionctl resource list
zionctl resource get <resource-id>
zionctl resource search <query>
```

These commands never sign or bypass governance.
